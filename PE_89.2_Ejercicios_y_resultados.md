# PE 89.2 — Ejercicios 1 y 2

## Ejercicio 1. Selección de la técnica adecuada

| Necesidad | Técnica | Justificación |
|---|---|---|
| Proteger un gran volumen de información cuando emisor y receptor ya comparten una clave secreta | Cifrado simétrico | El cifrado simétrico es rápido y eficiente para cifrar grandes volúmenes de información cuando ambas partes ya comparten una clave secreta. |
| Proteger un secreto destinado a un receptor sin haber acordado previamente una clave compartida | Cifrado asimétrico | El cifrado asimétrico permite enviar información confidencial sin compartir previamente una clave secreta, utilizando la clave pública del receptor para cifrar y su clave privada para descifrar. |
| Detectar si un archivo ha sido modificado | Función Hash | Permite comprobar la integridad de un archivo comparando su hash actual con un hash de referencia. Si el archivo cambia, su hash también será diferente. |
| Comprobar la identidad de un servidor web | Certificado digital | Permite comprobar que el servidor web es quien dice ser, verificando que el certificado corresponde al dominio y que ha sido emitido por una Autoridad de Certificación de confianza. |
| Acordar una clave compartida a través de una red insegura | Intercambio de claves Diffie-Hellman | Permite generar una clave secreta compartida sin transmitir directamente dicha clave por la red, por lo que resulta adecuado para establecer claves a través de canales inseguros. |
| Demostrar que un documento ha sido firmado por una determinada entidad y detectar modificaciones posteriores | Firma Digital | Permite verificar la identidad del firmante y comprobar que el documento no ha sido modificado después de su firma, aportando autenticidad, integridad y no repudio. |

## Ejercicio 2. Selección de una configuración segura

Se presentan tres configuraciones posibles para proteger una comunicación. Analízalas y responde a las preguntas.

| Configuración | Certificado / criptografía | Función hash | Protocolo y otras condiciones |
|---|---|---|---|
| **A** | Certificado RSA de 1024 bits | SHA-1 | TLS 1.0 |
| **B** | Certificado RSA de 2048 bits | SHA-256 | TLS 1.3 |
| **C** | Clave secreta incluida directamente en el mensaje | MD5 | HTTP sin TLS |

### 1. ¿Qué configuración seleccionarías para proteger una comunicación actual? Justifica la respuesta.

**R:** Seleccionaría la configuración B, porque utiliza algoritmos y protocolos adecuados para una comunicación actual. El certificado RSA de 2048 bits permite autenticar al servidor mediante criptografía asimétrica, SHA-256 proporciona una función hash robusta para comprobaciones de integridad y TLS 1.3 establece un canal cifrado y autenticado entre cliente y servidor que el certificado RSA 2048 es mucho mas seguro que el RSA de 1024, el MD5 ya es obsoleto.

### 2. ¿Por qué rechazarías las otras dos configuraciones? Identifica al menos un problema de seguridad en cada una.

**R: Configuración A:** La rechazaría porque utiliza tecnologías obsoletas. RSA de 1024 bits ofrece hoy un nivel de seguridad insuficiente, SHA-1 tiene vulnerabilidades conocidas frente a colisiones y TLS 1.0 es una versión antigua que ya no se considera segura para comunicaciones actuales.

**Configuración C:** La rechazaría porque es claramente insegura. MD5 no es adecuado para usos criptográficos modernos, HTTP sin TLS transmite la información sin cifrar y, además, incluir la clave secreta directamente en el mensaje hace que cualquiera que intercepte la comunicación pueda obtener también la clave.

### 3. Explica la diferencia entre cifrar un mensaje y calcular su hash.

**R:** Cifrar sirve para ocultar información y poder recuperarla después usando la clave adecuada. En cambio, calcular un hash sirve para obtener una huella digital del contenido y comprobar si ha sido modificado.

La diferencia principal es que el cifrado es reversible con una clave, mientras que el hash está diseñado para no poder revertirse.

### 4. ¿Qué propiedades de seguridad puede aportar un certificado digital dentro de una comunicación TLS?

**R:** Un certificado digital dentro de una comunicación TLS aporta principalmente autenticación, porque permite comprobar que el servidor es realmente quien dice ser.

Además, al vincular la identidad del servidor con su clave pública, ayuda a establecer una comunicación segura y a evitar suplantaciones o ataques Man-in-the-Middle. Junto con TLS, contribuye a garantizar confidencialidad e integridad de la comunicación.

openssl x509 -in certificado_servidor_PE89_2.crt -noout -fingerprint -sha256

## Ejercicio 2. Interpretación

### 1. ¿Es un certificado de servidor o un certificado de autoridad de certificación? ¿Qué campos permiten determinarlo?

Es un certificado de servidor.

Podemos comprobarlo porque en el campo **Basic Constraints** aparece `CA:FALSE`, lo que indica que no puede actuar como autoridad certificadora.

Además, en el campo **Extended Key Usage** aparece `TLS Web Server Authentication`, que indica que está destinado a autenticar un servidor web.

### 2. ¿Qué información del certificado permite relacionarlo con la identidad del servidor?

Principalmente los campos **Common Name (CN)** y **Subject Alternative Name (SAN)**.

En este certificado encontramos:

- **CN:** servidor.pe89.local
- **DNS:** servidor.pe89.local
- **DNS:** www.servidor.pe89.local
- **IP:** 172.28.0.30

Estos datos permiten comprobar que el certificado corresponde al servidor al que queremos conectarnos.

También aparece la organización `CETI Formacion`, que aporta información sobre la entidad identificada en el certificado.

### 3. ¿Qué parte del certificado puede distribuirse públicamente?

El certificado digital puede distribuirse públicamente, ya que contiene la clave pública y los datos necesarios para identificar al servidor y comprobar su firma.

La clave pública se puede compartir sin comprometer la seguridad de la clave privada.

### 4. ¿Contiene el certificado la clave privada asociada?

No. El certificado contiene únicamente la clave pública y la información de identificación del servidor, junto con otros datos y la firma de la autoridad certificadora.

La clave privada se guarda por separado y debe permanecer protegida.

### 5. ¿Qué riesgo existiría si la clave privada asociada al certificado fuera publicada o robada?

Si alguien consiguiera la clave privada del servidor, podría hacerse pasar por él y utilizarla para realizar operaciones criptográficas en su nombre.

Esto permitiría realizar ataques de suplantación y comprometer la seguridad de las comunicaciones.

Por este motivo, la clave privada debe mantenerse siempre protegida. Si se ve comprometida, es necesario revocar el certificado y generar uno nuevo con otra clave.

## Ejercicio 3. Verificación

Para comprobar que el certificado del servidor ha sido emitido por la autoridad certificadora proporcionada, se utiliza el siguiente comando:

```bash
openssl verify -CAfile CA_laboratorio_PE89_2.crt certificado_servidor_PE89_2.crt
```

### Salida obtenida

```text
certificado_servidor_PE89_2.crt: OK
```

### Explicación del resultado

El resultado `OK` indica que OpenSSL ha verificado correctamente el certificado del servidor utilizando el certificado de la autoridad certificadora del laboratorio.

Esto significa que la firma del certificado es válida, que la cadena de confianza se ha podido comprobar y que el certificado se encuentra dentro de su periodo de validez.

Por tanto, **la verificación se ha realizado correctamente** y el certificado del servidor está firmado por la CA proporcionada.

Esta comprobación utiliza la CA del laboratorio como entidad de confianza. No significa que el certificado sea reconocido automáticamente por los navegadores o por las autoridades certificadoras públicas.
